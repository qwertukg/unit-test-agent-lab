# Решения и статус

## Требования пользователя

- Много независимых продуктов/репозиториев GitLab, разные языки; это не один многомодульный проект.
- Роли окончательно называются Analyst, Coder, Reviewer.
- Обычный запуск только при провале unit coverage quality gate исходного MR feature → dev.
- Analyst добавляет сценарии (O6); Coder добавляет запускаемые тесты (O7).
- Reviewer проверяет всё, формирует отчёт (O8), публикует MR тестов в feature либо возвращает Analyst/Coder.
- Запускаемые тесты могут падать, выявляя дефект продукта. Нельзя подгонять ожидания ради зелёного CI.
- Обычная успешная генерация добавляет два основных рабочих объекта O6/O7 к исходным пяти. Отчёт Reviewer O8 и обратная связь O9 — дополнительные объекты процесса; не потерять их из-за старого выражения «+2».
- 👎 автора исходного MR на MR тестов запускает доработку с актуальными объектами; комментарий с меткой может уточнять замечания.
- Существующие объекты обновляются и версионируются, особенно junit/coverage после запуска тестов.
- Общие правила централизованы, проектные — в репозитории.
- Векторная БД пока не нужна. Долговременную обучающую память агентов пока не делать.
- Сохранять состояние процесса и восстанавливаться после сбоя.
- Цель: 3 независимых DGX Spark по 128 ГБ. Kubernetes и GitLab Runner уже есть; PostgreSQL вне Kubernetes.
- Локальный стенд в отдельной папке: Docker-сервисы, свой тестовый GitLab/Runner, реальные облачные модели, три контейнера вместо модельных серверов; автономная работа агента.
- Полная детальная блок-схема: нумерация с подномерами, ромбы для условий, цвет объектов, типы блоков, легенда с настоящими примерами стрелок. Компактная последовательная раскладка важнее обязательного LR.

## Архитектурная основа обсуждения

Python + FastAPI + LangGraph; отдельный LiteLLM Proxy. MCP для GitLab/YouTrack при наличии проверенного сервера и поддержки нужных операций, API/Git для остальных. Отсутствие MCP не должно блокировать локальный вертикальный сценарий.

## Предложения, не считать установленными фактами о готовом стенде

- Qwen3.8-27B NVIDIA NVFP4 как основная локальная модель; Flash-Next для сравнительного испытания. См. MODEL_NOTES.md.
- SGLang предложен вместо первоначального vLLM. Пользователь уточнил назначение, но никаких runtime ещё не развёрнуто. Проверить конкретную сборку перед переносом.
- Начать с одинаковой модели на всех Spark, без привязки роли к серверу.
- Изначальные ориентиры: 32–64K рабочего контекста, проверяемый предел 128K, 1–2 одновременных запроса на сервер. Это гипотезы для нагрузочных испытаний, не SLA.
- Защитные инженерные решения: дедупликация, контроль SHA, лимиты попыток/стоимости/времени, проверка допустимых изменений кодом, ручное слияние.

## Открыто на момент передачи

- Облачный провайдер, endpoint, model ID, API-ключ и бюджет ещё не выбраны/не переданы.
- ОС, CPU, свободная память, Docker и порты локального компьютера не проверены.
- Точные версии GitLab, Runner, библиотек и модели надо зафиксировать после реальной проверки.
- Формат метки комментария не определён: предлагается `@unit-test-agent`, настраиваемый.
- Доставка реакции 👎: проверить в установленной версии GitLab. Если нет нужного webhook, опрашивать award emoji API с курсором/дедупликацией.
- Какие языки демонстрации: рекомендуются Java/JUnit/JaCoCo и небольшой второй проект на Python; это предложение, не ограничение всех продуктов.
- Порог coverage: брать проектный; для демонстрации допустимо явно настроить 80%, не выдавая это за общий утверждённый порог.

## Изменения при передаче

Оригинальная диаграмма сохранена отдельно. В актуальной переименованы роли, добавлена явная исполняемая проверка перед публикацией, смена SHA возвращает к проверке coverage gate, облачная топология вынесена в отдельную схему. Это уточнения для согласованности с требованиями, не свидетельство работающей реализации.

## Решения реализации 27.09.2026

- Дополнение 28.09: пользователь подключил внешний локальный MTPLX вместо облака. MODEL_MODE=local, LiteLLM model prefix=openai/, цена 0 разрешена; все остальные лимиты сохранены. Worker включается только после реального capability probe. Текущие блокеры: отсутствие llguidance на сервере и timeout генерации; серверные настройки не менялись.

- После установки Docker пользователем реально запущены Linux Engine 29.8.0/Compose 5.5.1, GitLab/Runner, API/PostgreSQL/LiteLLM/три gateway. Два исходных MR и CI с coverage fail проверены; облачная модель по-прежнему не выбрана. Ранние записи ниже отражают состояние до установки Docker.
- Deadline начинается с первого исполнения (`started_at`), сохраняется в PostgreSQL и не сбрасывается при retry/restart/resume; ожидание в очереди не расходует runtime budget. Для ранее исполнявшихся записей миграция консервативно сохраняет старую точку отсчёта `created_at`.

- Хост проверен: Windows 11 x64, RAM 24 GiB. Docker/Desktop и WSL-дистрибутивов нет. Облако не задано. Это конкретные внешние блокеры полной приёмки; независимые компоненты реализованы и запускаются локально.
- Основной demo: Java/JUnit/JaCoCo/Maven; второй: Python/pytest. Project gate 80% diff line. Настройки/CI hashes централизованно проверяются. Исходные tests immutable, только отдельные новые test files.
- Очередь, события, версия объектов, actions и usage — PostgreSQL; checkpoints — реальный PostgresSaver LangGraph. В память процесса очередь не вынесена. Модель имеет только read/search/list tools snapshot.
- Реакции 👎 — polling canonical award emoji API; метка `@unit-test-agent`; stable award/note-body identities. Поздний комментарий ставится в следующий последовательный feedback run.
- Runner — отдельный TLS DinD, без host socket в agent/model/job. DinD privileged и не считается production sandbox; предпочтительная изоляция всего стенда — отдельная VM/context. Runtime GitLab bot отделён от root bootstrap.
- Реестр проверен: GitLab CE 19.4.1, Runner 19.4.0 и остальные images закреплены digest в `config/images.env`. Docker runtime пока не проверен. Python dependency lock включает LiteLLM 1.102.1, LangGraph 1.2.12 и PostgresSaver 3.1.2.
- Полная облачная приёмка, живые MR и Spark не объявляются пройденными. Подробная матрица и артефакты — VALIDATION.md.
