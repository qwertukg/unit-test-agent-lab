# Контекст обсуждения для следующего агента

Это структурированная сводка доступной переписки, **не полный дословный экспорт**. Не восстанавливает отсутствующие сообщения ассистента и не претендует на их точные формулировки. Короткие цитаты ниже — из видимых сообщений пользователя. Остальной текст — пересказ договорённостей.

## 1. От отдельных файлов к данным репозитория

Обсуждение началось с входных данных: diff недостаточно; нужны полные изменённые классы, конструкторы, контракты, типы, окружающая логика, зависимости, build.gradle(.kts)/pom.xml, версии, команды запуска и инструкции. Пользователь предложил получать весь репозиторий.

Позже уточнил: полный репозиторий в контексте модели может быть слишком большим. Репозиторий доступен агентам как рабочая копия, а в prompt попадают найденные релевантные данные. В отчёте Reviewer нужно показать, какие дополнительные файлы использованы.

Пользователь: «не много модульный проект. а много проектов в гитлабе, разных продуктов».
Разные языки и стеки; нельзя ориентироваться только на Rust/Python.
Пользователь: «общие правила - централизованные в агентой системе, но правила для проекта - в репозитории».

## 2. Формирование ролей и объектов

Изначально аналитик назывался QA/аналитик/сценарист, кодер — программист, Reviewer — QA Lead/финальный аналитик.

Пять исходных объектов: diff, отчёт unit-тестов, покрытие, задача/критерии и данные репозитория. Analyst создаёт готовые тестовые сценарии — шестой объект. Сценарии добавляются к общему контексту. Coder пишет по ним unit-тесты — седьмой объект.

Пользователь отдельно подчеркнул: результат Coder — **запускаемые** тесты. Часть может падать, если продукт содержит ошибку. Зелёный CI нельзя получать подгонкой теста под неправильное поведение.

Reviewer подбирает весь контекст, проверяет как запускались тесты и что показали, формирует отчёт по каждому объекту: diff, сценарии/тесты, запуск, покрытие, дополнительные данные репозитория. Выбирает публикацию MR тестов в feature либо доработку Analyst/Coder. В процессе обновляются и прежние объекты — особенно junit и coverage.

Позднее окончательные названия утверждены: **Analyst, Coder, Reviewer**. Использовать их во всём новом коде и документации.

## 3. Инфраструктура

Пользователь сообщил о трёх DGX Spark по 128 ГБ. Обсуждалась схема трёх независимых серверов моделей с распределением запросов агентной системой. Это не одна модель, разделённая на три узла.

Kubernetes уже готов. Пользователю удобно разместить два сервиса: LangGraph/FastAPI и LiteLLM Proxy. Runner можно поднимать по потребности; GitLab и Runner уже есть. PostgreSQL находится вне Kubernetes. GitLab планируется обновить. GitLab/YouTrack можно интегрировать через MCP; где операций не хватает — API/Git.

LangGraph и LiteLLM — разные компоненты: первый управляет workflow, второй маршрутизирует model calls. Runtime на Spark загружает и исполняет модель.

## 4. Поиск и память

Пользователь предложил векторную БД для индексирования репозиториев; после обсуждения решил: «для начала тогда не надо векторку».

Пайплайн пишется на Python, используется LangGraph. Обучающую агентную память на первом этапе не делать, но сбой не должен терять весь прогресс. Хранить checkpoints и сведения о внешних jobs/MR в PostgreSQL. Продолжение с этапа workflow отличается от продолжения точно с отдельного unit-теста внутри погибшего job.

## 5. Уточнение триггера

Пользователь: «пайп запускается только если QG по покрытию юнитами, MR не прошел».

Следовательно, исходные формулировки про создание MR/запуск pipeline не означают безусловную генерацию. Обычный агентный процесс стартует после подтверждённого провала gate покрытия. Другие сбои CI не эквивалентны coverage fail.

## 6. Обратная связь

Если автор исходного MR недоволен тестами, он ставит 👎 в MR тестов в feature. Пайп запускается снова с обновлёнными объектами. Автор может добавить комментарий с меткой, поясняющий проблему.

Не создавать очередной независимый MR при каждой доработке. Сохранить связь исходного MR и MR тестов, повтор обрабатывает актуальные сценарии/тесты/отчёты. Повтор по отзыву — отдельный триггер; нового QG fail не требуется.

## 7. Требования к диаграмме

Пользователь неоднократно просил полную подробную блок-схему с объектами, их движением, серверами, шагами и подшагами. Объекты другим цветом. В начале обсуждался LR, затем уточнение: «размещай элементы чтобы сократить длину ребра графа и при этом логично. не обязательно слева направо».

Условия должны быть ромбами (`id{"условие"}`), даже если текущий интерфейс отображает их иначе. Типы подписывать «объекты:», «действие:», «агент:», «сервер:» и т.п. Легенда на самой диаграмме, желательно вверху слева, с нарисованными примерами форм и стрелок, а не одним текстовым описанием. Положение в Mermaid зависит от renderer; порядок объявления сам по себе не гарантирует координаты.

Сохранена подробная .mmd; исходный файл включён в references. Актуальная копия в docs отражает последние названия и уточнения.

## 8. Исследование моделей

Пользователь потребовал серьёзный актуальный интернет-поиск, а не выбор по обучающей памяти модели. Предыдущая рекомендация ассистента: Qwen3.8-27B NVIDIA NVFP4 как основной кандидат, Flash-Next для сравнения; SGLang предложен вместо vLLM из-за опубликованных проверок Spark. Детали/URL в MODEL_NOTES.md.

Это рекомендация, а не установленная конфигурация или измерение на пользовательском железе. Пользователь спросил «мы это используем?» про SGLang. Ассистент пояснил: предложено, ничего не развёрнуто. При переносе проверять доступность весов, лицензий, runtime и совместимость ещё раз.

## 9. Запрос реализации и ограничение исходной сессии

Пользователь несколько раз попросил реализовать на его компьютере в отдельной папке полностью рабочий стенд с облачной моделью. Разрешил Docker-сервисы, GitLab в контейнере и эмуляцию трёх модельных серверов контейнерами. Попросил «делать все сам как агент» и затем «переключись на локальный кодекс и делай».

Проверки в исходной сессии показали только удалённый Linux workspace: Docker/podman и Docker socket отсутствуют, API-ключ облачной модели не найден. Открытие чата на компьютере пользователя не изменило доступ. Ассистент не может сам запустить локальное приложение пользователя. Поэтому реализация в той сессии не началась: ни сервисы, ни код стенда не созданы.

## 10. Текущая задача передачи

Пользователь спросил, как передать всю переписку. Предложены SPEC.md, AGENTS.md, диаграмма, PDF и сводка истории. Пользователь ответил «подготовь». Этот архив — результат именно подготовки контекста.

Следующий агент должен реализовать систему, а не заново спрашивать о каждой уже согласованной детали. Действительно незаданные параметры: облачный провайдер/модель/ключ, ресурсы локального хоста и конкретные версии компонентов. Всё остальное можно развивать самостоятельно в пределах требований.
