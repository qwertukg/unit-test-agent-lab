# Границы учебного стенда

- Только синтетические проекты. Корпоративный PDF использован как архитектурный контекст разных продуктов/стеков, его содержимое не передаётся модели.
- API/webhook требуют разные секреты. На хост опубликованы только loopback-порты 8000, 4000, 8929 и 2224. PostgreSQL, gateway и DinD наружу не опубликованы.
- Root GitLab bootstrap token остаётся в `.state/bootstrap.json`. В API/worker передаётся отдельный bot token пользователя с Developer-доступом только к двум demo-проектам. Модель получает ни GitLab, ни DB, ни host Docker credentials.
- Runner manager использует **отдельный DinD daemon с TLS**; job не получает Docker socket или client certificates. Job-контейнеры не privileged, имеют memory/CPU limit и разрешённый image. Network `host` относится к сетевому пространству DinD-контейнера, не к Windows host; это позволяет обращаться к `gitlab:8929`. Исполнение jobs последовательно.
- Сам DinD в Compose **privileged**. Это потенциальная возможность управлять Docker-хостом при escape. Учебная конфигурация не является производственной границей безопасности. Предпочтительно запускать весь стенд в отдельной disposable Linux VM/Docker context; никогда не подключать host Docker socket к модели или продуктовым тестам.
- Статическая проверка тестов и инструкция модели не превращают произвольный Python/Java в безопасный язык. Изоляция Runner обязательна. Job имеет свой GitLab CI_JOB_TOKEN и доступ к синтетическому проекту; production требует ограничить egress и scope job token, не передавать secret CI variables в недоверенные jobs.
- Tool API модели: только список файлов, чтение и буквальный поиск в snapshot. Symlink, path traversal, `.env`, `.git` и credential directories отвергаются. Команд shell/network tools нет. Coder не может менять существующие файлы исходного SHA, зависимости/CI/QG; допускаются только новые `test_agent_*.py` или `Agent*Test.java`.
- Model logs содержат role/endpoint/latency/usage, без ключей и полных prompts. Не выводить `docker compose config` без `--quiet`: он интерполирует локальные секреты. Не публиковать `.env`, `.state`, PostgreSQL data, runtime config Runner и cloud response dumps.
- GitLab HTTP и secrets в `.env` допустимы только для локального loopback-стенда. Production — TLS, secret manager, минимальные права БД и project-scoped bot.
- Portable PostgreSQL для локальных тестов использует trust **только 127.0.0.1:55432** и временную БД. Это независимый тестовый компонент; после проверки остановить `pg_ctl -D .state/pgdata stop`. Не использовать его trust-конфигурацию в deployment.
