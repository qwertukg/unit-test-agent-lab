# Техническое задание: Unit Test Agent Lab

Версия передачи 1.0 · 27.09.2026 · Статус: требуется реализация и проверка.

## 1. Цель

Автоматизировать подготовку осмысленных unit-тестов для нового кода исходного MR feature → dev, не прошедшего quality gate по покрытию. Результат — отдельный MR с тестами в исходную feature-ветку, отчёт Reviewer и ссылки на фактический запуск/покрытие. Решение должно обслуживать много независимых репозиториев разных продуктов и языков.

Первый этап — полностью рабочий локальный Docker-стенд с реальной облачной LLM и синтетическими продуктами. Второй этап — перенос оркестрации в существующий Kubernetes и замена облачных endpoints на три независимых DGX Spark (128 ГБ каждый). Не объединять Spark в общую память и не требовать tensor parallelism для базового сценария.

## 2. Топология

| Компонент | Локальный стенд | Целевая среда |
|---|---|---|
| GitLab | Отдельный Docker-сервис, persistent volumes | Существующий GitLab |
| Runner | Зарегистрированный локальный исполнитель с изоляцией jobs | Существующие Runner |
| Agent service | Python, FastAPI, LangGraph; долговечный worker | Kubernetes |
| LiteLLM Proxy | Отдельный сервис | Отдельный сервис Kubernetes |
| spark-1/2/3 | Три независимых API-шлюза к облаку | Три сервера SGLang + локальная модель; runtime проверить |
| PostgreSQL | Контейнер с persistent volume | Внешняя БД вне Kubernetes |
| Артефакты | GitLab artifacts / постоянное хранилище | GitLab artifacts / согласованное хранилище |
| YouTrack | Явный demo adapter с фикстурой либо настроенный тестовый доступ | MCP/API adapter |

Три шлюза имитируют сетевой контракт и отказ одного endpoint, но не GPU, объём RAM или производительность Spark. Общий upstream-провайдер может иметь общий rate limit: наличие трёх шлюзов его не утраивает. Cloud mode и local mode используют один контракт вызова модели.

GitLab может требовать отдельной архитектуры образа/ресурсов; не предполагать, что любой официальный образ работает на ARM. При переносе на Spark переносится модельный сервис, а не обязательно GitLab. Конкретные ограничения хоста проверить до развёртывания.

## 3. Объекты и версии

Использовать стабильные обозначения ASCII `O1`–`O9` в коде. Кириллическое «О» в исходной диаграмме означает те же объекты.

| ID | Краткое имя | Содержание | Создание и обновление |
|---|---|---|---|
| O1 | Diff | Diff исходного MR; base/head SHA, пути и диапазоны изменений | При сборе и смене исходной ревизии |
| O2 | TestReport | JUnit/эквивалент, тесты, ошибки, статус сборки, job/pipeline ID, логи | Исходный CI; после каждого проверочного запуска |
| O3 | Coverage | Покрытие строк/ветвей, diff coverage, порог, результат QG, отчёт и инструмент | Исходный CI; после каждого запуска; отсутствие = явная ошибка, не 0/старый успех |
| O4 | Task | Требования, критерии приёмки, issue ID/ссылка, версия снимка | При сборе, при изменении требований |
| O5 | Repo | Репозиторий на точном SHA; код, тесты, фикстуры, зависимости, сборка, проектные правила | Исходная ревизия и ссылки на проверочные ревизии |
| O6 | Scenarios | Сценарии, предусловия, входы, ожидаемое поведение, негативные случаи, трассировка к требованиям | Analyst, затем его доработки |
| O7 | Tests | Файлы/patch unit-тестов, manifest изменений, commit/hash версии | Coder, затем его доработки |
| O8 | Review | Проверка каждого объекта, замечания, обнаруженные дефекты, решение и обоснование | Reviewer на каждой итерации |
| O9 | Feedback | Реакция автора, tagged-комментарии, автор/ID/время события, ревизия MR | По событиям обратной связи |

Для каждой версии сохранять: object ID, version, run ID, iteration, project/MR, source SHA, при необходимости test commit SHA, created_at, producer, content hash, место хранения, связи с входными версиями. Не затирать прошлые версии.

O1 — изменения исходного продукта; diff сгенерированных тестов хранится в O7. Не смешивать их. O2/O3 исходного CI и O2/O3 проверки O7 различать через происхождение и SHA; не сравнивать отчёты разных деревьев как один запуск.

Полный контекст первого Analyst: O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo.
Первого Coder: O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo, O6 Scenarios.
Первого Reviewer: O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo, O6 Scenarios, O7 Tests.
Повторного Reviewer: O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo, O6 Scenarios, O7 Tests, O8 Review, O9 Feedback — если отзыв уже получен.
При возврате Analyst/Coder доступен весь существующий набор этих объектов, а не только последнее замечание.

«Общий контекст» — доступность версий/ссылок и инструментов, а не буквальная вставка полного репозитория и всех логов в каждый prompt. Repo можно клонировать целиком; в модель передавать релевантные файлы, полные классы и зависимости по необходимости. Поиск через rg/файловые инструменты, без векторной БД. Фиксировать использованные пути и ревизии для отчёта.

## 4. Триггеры

### 4.1. Обычный запуск

1. Создан/обновлён MR feature → dev. Runner выполняет штатные тесты и coverage QG.
2. Получены завершённые и согласованные отчёты на актуальном SHA.
3. Именно QG unit coverage не пройден. Одного статуса «pipeline failed» недостаточно.
4. MR разрешён конфигурацией, не является MR самого агента. QG passed, неизвестный QG, сбой инфраструктуры или отсутствие отчётов сами по себе не запускают генерацию.
5. Проверены event deduplication и отсутствие параллельной работы с той же исходной ревизией.

Не делать постоянную генерацию при каждом push и не вводить nightly schedule: позднее уточнение пользователя задаёт gate-trigger.

### 4.2. Повтор по отзыву

Новая реакция 👎 автора исходного MR на MR с тестами запускает доработку независимо от повторного провала QG. Комментарий с меткой опционален. Проверить автора по GitLab user ID, не по display name. Чужая реакция не является таким триггером.

Зафиксировать стабильный ID реакции. Повторная доставка не повторяет работу. Удаление/повторное добавление учитывать по новой идентичности события. Поздний tagged-комментарий сохранить и добавить в активную/следующую итерацию без потери. Если итерация уже идёт, не создавать второй конкурентный writer.

Если MR закрыт/слит, не открывать его молча заново; сохранить событие и понятный статус. Точный UX позднего комментария документировать. Самостоятельный запуск только по комментарию — дополнительная опция, не подмена требования по 👎.

## 5. Переходы

### 5.1. Сбор

Зарегистрировать run, версии правил, исходный MR, автора, SHA и базу diff. Получить O1–O5, проверить их соответствие. Подготовить workspace на точном SHA и инструменты чтения/поиска. Если данных не хватает — явный blocked с причиной, не выдуманные требования/отчёты.

### 5.2. Analyst

Изучает O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo; при доработке также O6 Scenarios, O7 Tests, O8 Review, O9 Feedback. Читает существующие тесты и соглашения проекта. Создаёт/обновляет O6: ID сценария, цель, связь с diff/требованием, подготовка, входы, ожидаемый результат, негативные/граничные случаи, допустимые моки. Сохраняется структурированный валидируемый результат.

### 5.3. Coder

Использует сценарии и все доступные объекты. Пишет/дорабатывает тесты в отдельной рабочей копии, создаёт O7. Допустимые пути/операции проверяются кодом. Запрещено менять продукт, отключать assertions/старые тесты, менять QG или coverage exclusions ради результата. Необходимые новые зависимости — отдельное явно контролируемое расширение политики, не произвольное разрешение LLM.

### 5.4. Проверка Runner

Сохранить версию O7, подготовить проверочный commit/ref, зарегистрировать intent и job/pipeline ID. Runner собирает и запускает на точном сочетании source SHA + test revision. Сохраняет O2/O3 и логи даже при падениях. Нельзя публиковать ссылку на успешный исходный CI как доказательство запуска новых тестов.

Инфраструктурная ошибка → ограниченный retry того же проверяемого состояния. Ошибка компиляции/запуска тестов → Coder с реальными логами. Запускаемые тесты с failing assertions → Reviewer: это может быть дефект продукта. Лимит времени/попыток/стоимости → отчёт и needs_human. Лимит времени отсчитывается от устойчивого `started_at` первого исполнения; ожидание в очереди до него не расходует бюджет. Retry/restart/resume не сбрасывают `started_at`.

### 5.5. Reviewer

Проверяет каждый объект и трассировку от требований к сценариям и assertions; осмысленность покрытия, моки, фактический запуск, причины падений, актуальность SHA, отзыв автора. Формирует O8 с выводами по O1 Diff, O2 TestReport, O3 Coverage, O4 Task, O5 Repo, O6 Scenarios, O7 Tests, O8 Review предыдущей версии и O9 Feedback при наличии.

Три штатных решения: `publish`, `revise_scenarios`, `revise_tests`.
`revise_scenarios` → Analyst → Coder → Runner → Reviewer.
`revise_tests` → Coder → Runner → Reviewer.
Техническая остановка/исчерпание лимита — статус системы, а не четвёртая творческая роль.

LLM не является единственным quality gate. Детерминированный код проверяет разрешённые файлы, новые результаты на нужном SHA, отсутствие конфликтов и свежесть целевой feature, наличие нужных артефактов. Пустой результат не считать MR успехом.

Если новые корректные тесты выявили дефект продукта, сохранить доказательство и эскалировать. По умолчанию не публиковать обычный «всё хорошо» MR с failing CI. Draft MR для демонстрации дефекта — настраиваемая отдельная политика, исходно выключена. Не требовать от Coder ложного зелёного результата.

### 5.6. Публикация

Перед публикацией перечитать SHA feature и состояние исходного MR. Если SHA изменился, старые проверки не действительны. Для обычного запуска вновь проверить eligibility/QG новой ревизии; если gate пройден — остановить генерацию. Для доработки по отзыву обновить контекст и проверить необходимость продолжения отдельно. Нельзя бесконечно публиковать устаревшие тесты.

Создать/обновить ветку `ai-tests/<source-mr-id>` (конкретное имя настраивается) и MR в исходную feature. Один активный MR тестов на исходный MR; повтор использует его. Проверочные ref/job могут существовать до публикации, но не должны сами запускать генерацию.

MR содержит O7, O8, ссылки на O2/O3, source SHA/test SHA, исходный MR и задачу. Человек принимает/сливает; обязательные проверки GitLab сохраняются. Не выполнять auto-merge. После слияния повторный исходный CI снова оценивает QG с защитой от дубликатов/бесконечного цикла.

## 6. Состояние и восстановление

Нужны persisted checkpoints LangGraph плюс устойчивое состояние запусков, событий, lease/lock, объектов, внешних actions. Очередь можно реализовать через PostgreSQL; конкретный механизм выбирает агент, но он обязан переживать restart.

Сохранять pending/completed action intent до/после внешнего побочного эффекта. Если процесс упал между созданием job/MR/commit и сохранением ответа, при старте искать уже выполненное действие по устойчивой идентичности, а не слепо повторять.

- Existing job running → продолжить ожидание.
- Existing job completed → получить артефакты и продолжить граф.
- Job не был создан → создать один раз после reconciliation.
- Незавершённый LLM call → допустим ограниченный повтор; учесть возможное повторное списание в облаке.
- Погибший тестовый процесс → обычно повторяется job/набор тестов. Обещать продолжение ровно с конкретного теста нельзя без поддержки тестового framework.

Это операционная память workflow, не обучающая агентная память. Не делать автоматическое пополнение общих правил или MR инструкций по результатам принятых тестов в этом этапе.

## 7. Инструменты и конфигурация продуктов

Центральные правила: роли, policy, разрешения, лимиты, версии prompts. Проектная конфигурация: stack, build/test commands, пути тестов, отчёты, coverage metric/threshold, правила mock/fixtures и ссылки на инструкции.

Нельзя жёстко зашить pytest или Gradle во все проекты. Предусмотреть adapters для запуска и нормализации отчётов; подтвердить хотя бы основной JVM-сценарий и ещё один стек для проверки расширяемости (предложенный объём MVP).

MCP использовать там, где реальная установленная интеграция поддерживает операцию. API/Git — допустимый fallback. Не реализовывать фиктивный «MCP» endpoint ради галочки. Доступ к YouTrack в демонстрации может быть fixture adapter с честным статусом; live adapter должен иметь конфигурируемый контракт.

## 8. Интерфейсы и эксплуатация

Предусмотреть health/readiness, приём проверяемых GitLab событий, просмотр run/status/object versions, повтор с сохранённого этапа, отмену и ограниченные admin операции. Аутентификация и webhook secret должны проверяться. Не отдавать секреты и исходники без контроля доступа.

Bootstrap повторяемый: volumes, migrations, тестовый GitLab project, runtime bot, Runner, проектные переменные, webhooks, demo branches/MR. Привилегии bootstrap отделены от штатного bot. Не использовать root token во всех сервисах. Документировать пользовательские адреса отдельно от docker service DNS и clone URL Runner.

Модель: конфигурируемые base_url/model/key, таймауты, token/cost limits, max tool steps. Проверять реальные tool calls и structured output, не считать endpoint совместимым лишь по /health. Три gateway адреса независимы; прокси не обязан всегда выбирать «самый свободный» без соответствующей настройки маршрутизации.

Логи с run_id/iteration/role/job_id/endpoint, latency и usage без секретов. Крупные artifacts не складывать бесконтрольно в prompt/checkpoint. Retention не должен удалять необходимые данные активных runs.

## 10. Конкретизация MVP реализации (27.09.2026)

Исходные требования выше сохраняются. Эти пункты фиксируют выбранный контракт, а не отменяют непроверенные критерии приёмки.

- PostgreSQL queue/events/actions/object versions + PostgresSaver; session advisory lock по project/MR и recovery lease 180 секунд. Реальный код графа — `agent_lab/workflow.py`; API и worker — отдельные процессы. В Kubernetes они входят в один Deployment с двумя containers.
- Demo stacks: Java/JUnit/JaCoCo через Maven и Python/pytest/Cobertura. Gate — 80% изменённых исполняемых строк относительно base исходного MR; total line coverage сохраняется отдельно. Новые команды/стек регистрируются reviewed adapter/config; `.test-agent.json`, CI entrypoint и build file hashes закреплены центрально. CI запускает argv без shell-строки от модели.
- Узкая политика O7: только новые `Agent*Test.java`/`test_agent_*.py` в test roots относительно source SHA. Исходные tests не редактируются. Повтор Coder меняет полный manifest собственных файлов; новые dependencies запрещены без отдельного расширения policy.
- Проверочный commit в immutable `agent-verify/<mr>/<run>/<iteration>-<attempt>` создаёт единственный push pipeline. Автоматический CI на `ai-tests/*` не запускает генерацию. Публикация exact tested commit — Git push force-with-lease; stable MR marker и отдельные intents для commit/pipeline/push/MR/description. Обычный MR с failing CI не публикуется, draft-defect policy не включена.
- Реакции читаются `/projects/:id/merge_requests/:iid/award_emoji` с durable dedupe по award ID; optional webhooks ускоряют canonical API reconciliation. Периодический опрос — доставка событий, не nightly генерация.
- Метка комментария — `@unit-test-agent`. До первого авторского 👎 комментарии только сохраняются; после него поздний/изменённый tagged-комментарий запускает последовательный feedback run. Текущий model call не прерывается. Новый run использует последний опубликованный контекст, закрытый/слитый MR не открывается заново.
- O1–O9 размещены в PostgreSQL `lab_objects` (immutable row ID, версии, hashes, inputs, SHA, producer, timestamp); полные JUnit/coverage/logs — в GitLab artifacts. JSON schemas экспортированы в `schemas`. Крупные raw reports не помещаются в checkpoint/prompt.
- Cloud gateways используют LiteLLM provider adapters; единый внешний контракт — chat completions, tools и JSON output. При переносе gateway заменяется SGLang endpoint через `deploy/kubernetes/litellm.yaml`; роли не меняются. Совместимость конкретной cloud model/Spark требует реального probe.
- JSON transport выбирается явно: `MODEL_JSON_MODE=json_object` отправляет native response_format, `prompt` передаёт schema в системном сообщении без response_format. В обоих режимах итог строго проверяется Pydantic; невалидный ответ не сохраняется как завершённый. Один запрос исправления формата допустим только в оставшемся бюджете шагов/токенов/вызовов; повторная ошибка останавливает run. После `max_tool_steps` раундов последний запрос имеет `tool_choice=none`; дополнительные tool calls отклоняются. Бюджет запросов не увеличивается.
- 28.09.2026 пользователь выбрал для текущего стенда внешний локальный MTPLX endpoint вместо облачного провайдера. `MODEL_MODE=local` допускает нулевую цену, сохраняя token/call/time limits; три gateway направлены к одному upstream. Это не подтверждение трёх физических Spark или облачной приёмки. Bootstrap запускает worker только после реальных JSON/tool probes; ошибки сервера не заменяются mock.
- `TOKEN_PRICE_UPPER_USD` задаёт оператор. Токены/стоимость учитываются консервативно с запасом на два proxy retry; неуспешный неоднозначный вызов сохраняет резерв. Точные расценки и скорость не выдумываются.

Детали эксплуатации — `docs/RUNBOOK.md`, границы Runner/DinD — `docs/SECURITY.md`, реальный статус — `VALIDATION.md`.
